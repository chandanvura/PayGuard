01 / THE PROBLEM

Did the charge happen?

A provider may process a payment and time out before returning its response. Retrying blindly risks a second charge. PayGuard records UNKNOWN, queries the simulated provider later, and resolves the original payment to SUCCESS. A retry with the same idempotency key receives the same payment ID.

01ChargeClient sends a unique key
02TimeoutProvider records success; response is lost
03UnknownAPI persists uncertain state
04ReconcileWorker checks provider status
05RecoveredSame ID resolves to SUCCESS
02 / SYSTEM MAP

One flow, several layers.

REQUEST PATH

Client → API → provider

Spring Boot validates requests and persists state in PostgreSQL. Flyway owns schema changes. A fake provider supports repeatable failure scenarios without financial transactions.

RECOVERY PATH

UNKNOWN → worker → SUCCESS

The reconciliation worker revisits uncertain payments. Persistent idempotency keys tie retries to the existing payment.

OPERATIONS

Docker → Kubernetes

Compose runs the local stack. Minikube demonstrates health probes, persistent storage, scaling, self healing, rolling updates, and rollback.

OBSERVABILITY

Metrics + logs

Micrometer exposes metrics to Prometheus; recording and alerting rules track SLI/SLO signals. Alloy sends scoped container logs to Loki. Grafana displays both.

04 / REPRODUCIBLE EVIDENCE

Run it without my laptop.

GitHub Actions starts PostgreSQL and the Java service on a temporary runner. It checks health, a normal payment, timeout after charge, UNKNOWN state, duplicate retry, automatic reconciliation, and exported metrics. Each run publishes a summary and downloadable logs for 30 days.

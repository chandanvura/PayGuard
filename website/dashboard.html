01 / PAYMENT SCENARIO

One payment. No duplicate charge.

SELECTED STEP

Client sends payment

The client POSTs a payment with an Idempotency-Key. That key identifies this logical payment across retries.

PAYMENT STATENEW REQUEST
POST /api/v1/payments
Idempotency-Key: DEMO-TIMEOUT-...
{ "customerId": "CUSTOMER-DEMO", "amount": 149900, "currency": "INR" }
WHAT TO NOTICE

The key belongs to the payment attempt, not to a single HTTP connection.

02 / MONITORING PANELS

Ask the right operational questions.

AVAILABILITY SLI

Are payment requests succeeding?

Prometheus records a five-minute ratio and compares it with a 99.9% availability objective.

payguard:sli_availability:ratio5m
ERROR BUDGET

How fast is it burning?

The burn rate relates observed error ratio to the allowed 0.1% error budget. Warning and critical rules evaluate it.

payguard:slo_availability:burn_rate5m
LATENCY SLI

Are requests fast enough?

A five-minute ratio tracks responses within 250 ms; the latency alert evaluates a 99% threshold.

payguard:sli_latency_250ms:ratio5m
LOGS AND RECOVERY

What happened to this payment?

Alloy ships scoped PayGuard logs to Loki. Provider and reconciliation events help explain the UNKNOWN → SUCCESS transition.
